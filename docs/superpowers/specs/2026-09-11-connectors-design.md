# Database and SSH connectors behind the Vault

Date: 2026-09-11. Status: built on a worktree branch for the lead session to merge; `npm install` (pg, mysql2, ssh2 are optional) and a restart follow the merge.

## Problem

The Vault (2026-09-11, "The Vault: a secret store agents use without seeing") stores database connections and SSH targets, but agents could only reach outside services (`api_get`, `api_request`, `api_upload`). A Finance task that needs a number from the ledger's database, or an Operations task that must pull a deployment on a server, had to stop and ask the CEO to do it by hand. The Bayanatkom intranet's DB Intelligence module already solved this for its chat: a query validator, a connection pool with a circuit breaker, an SSH executor with an allow list, and an approval step for anything that changes something. This ports the model into the office, as Node modules, wired to the Vault and to the leads' and specialists' tools, without a live database or server in the tests.

## Design

### 1. `connectors/database.mjs`
- `validateQuery(sql, { readOnly })` → `{ ok, sql, reason, kind: 'read' | 'write', warning? }`. Text and quoted names are blanked first (`maskLiterals`; Postgres quoting, no backslash escapes, dollar quotes), so nothing inside a string counts. Refused always: an empty statement, one over 20,000 characters, a comment (`--`, `/* */`, `#`), a second statement, an unclosed quote, and DROP, TRUNCATE, ALTER, GRANT, REVOKE, CREATE, RENAME, COPY … PROGRAM, LOAD DATA, INTO OUTFILE and the file, sleep, link and code functions (pg_read_file, dblink, pg_sleep, xp_cmdshell, …). Reads are SELECT, WITH … SELECT, SHOW, EXPLAIN and DESCRIBE; a read may not contain INSERT, UPDATE, DELETE, MERGE, INTO, LOCK, CALL, EXEC, nextval and the like (a write hiding in a CTE, a FOR UPDATE lock, SELECT INTO). Writes are INSERT, UPDATE, DELETE, MERGE and REPLACE, accepted only when `readOnly` is false. Anything else (VACUUM, SET, a bare COPY) is not a statement an agent runs. A SELECT or WITH without LIMIT or FETCH FIRST gets ` LIMIT 200`; an UPDATE or DELETE without WHERE carries a warning for the CEO.
- `CircuitBreaker({ failures = 3, openMs = 60000, now })`: closed → open after three failures in a row → half-open after a minute, one probe at a time; success closes it, a failure while half-open opens it again. An open circuit refuses with the seconds left.
- `DatabasePool({ drivers, loaders, breaker, now })`: one lazily created client pool per Vault entry id, rebuilt when the entry's engine, host, port, database, user, password, read-only flag or SSL changes (compared by a SHA-256 fingerprint, the password is not kept twice), closed on replacement and on `close()`. `query(entry, sql, { timeoutMs = 15000 })` and `schema(entry)` run through the entry's breaker. Engines: `postgres` (pg) and `mysql` (mysql2), both loaded with a dynamic `import()` on first use; a missing package is the plain sentence "install pg to use Postgres connections" / "install mysql2 to use MySQL connections". `drivers` (engine → `async entry => adapter`) lets tests inject fakes; `postgresAdapter(pg, entry)` and `mysqlAdapter(mysql, entry)` are exported so the real wiring is tested with fake modules too.
- Postgres: `Pool({ max: 2, connectionTimeoutMillis: 10000, idleTimeoutMillis: 60000, options: '-c default_transaction_read_only=on' })` for a read-only entry (defence in depth: the server refuses a write the validator missed), `SET statement_timeout` per query, `rowMode: 'array'`, a client that failed is released with the error so the pool drops it. MySQL: `createPool({ connectionLimit: 2, rowsAsArray: true })`, `SET SESSION TRANSACTION READ ONLY` for a read-only entry, `SET SESSION MAX_EXECUTION_TIME`, a failed connection is destroyed. Both get a JavaScript-side timeout two seconds after the server-side one. Schema: `information_schema.columns` joined to `information_schema.tables` (all schemas but the catalogue for Postgres, the current database for MySQL), grouped by `tablesFrom` into `{ schema, name, type, columns: [{ name, type, nullable }] }`.
- What an agent gets back (`capResult`): at most 200 rows and 100 KB of text, cells cut at 500 characters, `truncated` set when anything was left out; `markdownTable` renders it with a footer ("12 rows in 34 ms; the result was cut …"), `schemaText` renders tables as headings and column lines.

### 2. `connectors/ssh.mjs`
- `validateCommand(command, entry)` → `{ ok, command, reason }`: empty, over 2,000 characters or multi-line is refused; the deny list (`rm -rf /`, `mkfs`, `dd if=`, `shutdown`, `reboot`, `halt`, `poweroff`, `init 0|6`, `:(){` fork bombs, `> /dev/sd…`, `chmod … 777 /`, `wipefs`) is refused whatever the entry allows; an entry with `allow` (command prefixes such as `git pull`, `systemctl status`) runs only a command that starts with one of them, and then no chaining or redirection (`; & | \` $ < >`), since `git pull; rm -rf ~` starts with an allowed prefix. The intranet compared the executable token; the office compares the prefix the CEO typed, which reads the way the CEO wrote it.
- `SshRunner({ loader, connectTimeoutMs = 15000 })`: `run(entry, command, { timeoutMs = 60000 })` → `{ code, signal, stdout, stderr, ms, timedOut, truncated }` through ssh2 (`loader` imports it; a missing package is "install ssh2 to use SSH targets"). A secret that starts with `-----BEGIN` is a private key, anything else a password (with keyboard-interactive as a fallback). stdout and stderr keep their first 50 KB. A command still running at the limit is cut off: the connection is closed and the answer says it was stopped. An entry may pin the host key (`fingerprint`, `SHA256:…` as `ssh-keygen -lf` prints it); then `hostVerifier` refuses a host whose key differs. Without a fingerprint the host key is not checked, as in the intranet's first version; pinning on first use is a follow-up.

### 3. The engine (`engine/deep-agents.mjs`)
- `OfficeEngine({ connectors: { pool, ssh } })`, defaulting to `new DatabasePool()` and `new SshRunner()`; `close()` closes the pool.
- `connectorTools(jobId, team, agentId)` returns six tools for every lead and specialist, built like `vaultTools` and empty when the office has no Vault: `db_list` (the database entries the team may use: id, engine, host, database, user, read-only or writable, whether a password is stored), `db_schema({ database })`, `db_query({ database, sql })` (validated against the entry's read-only flag; a write is refused with "call db_write"), `db_write({ database, sql, why })` (refused on a read-only entry, validated with `readOnly: false`, must be a write), `ssh_list`, `ssh_run({ target, command })`. An entry limited to other teams is not offered and not reachable by id. Every answer goes through `vault.mask`; every call records `connector_called` on the task's timeline (statement or command cut at 120 characters, rows or exit code, milliseconds, the `why` of a write), also masked. Errors come back as one sentence ("The query on ops-db failed: …"), never as a throw.
- `VAULT_APPROVALS` now holds `api_request`, `api_upload`, `db_write` and `ssh_run`: a data change and a command pause for the CEO through Deep Agents' `interruptOn` like every outbound action; `db_list`, `db_schema` and `db_query` run at once. The CEO sees the raw arguments (the statement, the `why`) before approving; validation runs when the tool runs, so a DROP the CEO approved by mistake is still refused.
- Prompts: the shared FILES paragraph names the six tools, says which pause, and forbids putting a password or a key in a statement or a command.

### 4. The Vault (`vault.mjs`, `src/settings.js`)
- A database entry carries `engine` (postgres or mysql only, refused otherwise; the port defaults to 5432 or 3306) and `readOnly` (default true; a later edit that does not mention it keeps the choice; "false", 0 and "off" count as false). An SSH entry carries `allow` (an array or one prefix per line; blanks and repeats dropped; at most 50) and `fingerprint` (optional).
- Settings → Vault: the engine is a choice (Postgres, MySQL / MariaDB), a Read-only tick box for a database, an Allowed commands textarea and a Host key fingerprint field for an SSH target; the list shows read-only / writable and the number of allowed prefixes.

### 5. Tests (`tests/connectors.test.mjs`, 10 tests; `tests/vault.test.mjs` and `tests/prompts.test.mjs` extended)
The validator (allow and refuse cases, LIMIT injection, literals, CTE writes, locks, blocked functions), the breaker with a fake clock (open, refused without a call, half-open probe, reopen, close), the pool with an injected fake driver (one client per entry, rebuild on change, the caps, a missing package, the breaker around it), the two real adapters with fake pg and mysql2 modules (read-only session, timeouts, array rows, dropping a failed client, schema grouping), the SSH validator with and without an allow list, the runner with a fake ssh2 (key versus password, fingerprint pinning, output cap, a hung command cut off, a refused login, a missing package), the Vault fields, the engine tools with fakes (a team-limited entry hidden, a read run with the LIMIT added, a write refused on a read-only entry and run on a writable one, masking, timeline events without secrets, no Vault → no tools, missing packages → a sentence), and a build with a capturing agent factory (leads and specialists carry the tools, `db_write` and `ssh_run` interrupt, `db_query` does not, the Program Manager has none).

## What the intranet's tool-definition model teaches for the office's MCP connectors

Read in `backend/onyx/db_intelligence/` (models.py, tool_permissions.py, api/tool_definitions.py, api/mcp_tools.py, api/ssh_tools.py, api/tools.py, connectors/ssh.py, query_validator.py, circuit_breaker.py, connection_pool.py) and `web/src/app/api/db-intelligence/` (tool-registry.ts, chat/route.ts, tools/*.ts, chat/approval-execution-cache.ts). Nothing from the vault folders was opened.

- **One record for every kind of tool.** `DbIntelToolDefinition`: `alias` (lowercase, used as an @mention), `display_name`, `type` ∈ database | ssh | mcp | http | email | enterprise_search, `config_encrypted` (Fernet-encrypted JSON whose shape depends on the type), `enabled`, `status` (unknown / connected / error, with `last_status_check` and `status_message` from a test endpoint), `created_by_user_id`, and `requires_approval_actions_json`. The last field exists in the model and the API response, but nothing reads it: approval is decided per tool family in code (below). Lesson: an "actions that need approval" field per connector is the right shape for the office's Approval rules, but it only means something if the runtime reads it; the office's `outboundTools` / `readOnlyTools` settings already are that field, kept in `settings.json` rather than on the connector.
- **Permissions are tiers, per user and per group.** `view` < `execute` < `manage` < `admin`; the creator is admin, an org admin is admin everywhere, otherwise the highest of the direct grant and the group grants. Reads need view; SSH command / file write / delete and MCP invoke need execute; a SQL write needs manage; editing the definition needs manage, deleting admin. `list_accessible_tool_definitions` returns the definitions with a permission map, so the front end knows what to offer. The office has one tier ("this team may use it"); a second tier ("may only read") per team would map onto the same `toolsFor({ readOnly })` path that already exists for leads' spot checks.
- **MCP config shape.** `{ transport: 'stdio' | 'sse' | 'http', command, args (an array, a comma-separated string, or "command with args" in one string), env: { k: v } }` for stdio; `{ server_url | url, headers: { k: v } }` for the URL transports; plus `auto_include: true` for a server every conversation gets without an @mention. Secrets inside a config are masked in API responses by key name (`password`, `private_key`, `token`, `bearer_token`, `api_key`, `auth_token`, `authorization`), never by value.
- **MCP tools are pooled, prefixed and, notably, not gated.** One MCP client per (definition id, transport, target, headers or env) with a 5-minute TTL, refreshed in the background, the old client closed after a 60-second grace so a stream in flight finishes; failures keep the stale client rather than dropping the tools (the office's `ToolHub.load` retirement does the same thing for the same reason). Discovered tools are exposed to the model as `<alias>__<tool name>` so two servers with the same tool names do not collide; the office keeps raw names and would collide. MCP tools keep their `execute` and run without approval; only `executeSQLWrite`, `sshExecuteCommand`, `sshWriteFile`, `sshDeleteFile` and `sendEmail` are HITL tools. The office is stricter here already (every MCP tool is classified outbound or read-only from its name, description and `readOnlyHint`, with the CEO's override per tool).
- **How HITL works there.** A gated tool is defined without `execute()`, so the Vercel AI SDK stops the stream; the UI shows a card; the decision is the literal string "Yes, confirmed." or "No, denied." in the tool result; on the next turn the server executes confirmed calls against the backend, which re-checks the permission tier, the connection's `read_only` flag and the validator, and rate-limits per user. An `approval-execution-cache` keyed by (conversation, tool call id) with a 24-hour TTL makes a confirmed call run once even when the message history is replayed. A skill invoked explicitly (a typed `/command` or an @mention) whose metadata says `approval.required: false` skips the destructive-tool gate; a keyword-triggered skill never does. The office's equivalent is Deep Agents' `interruptOn` plus the task's `pendingActions`; a restart replays the graph from its checkpoint, so an approved tool call is not repeated, but there is no explicit run-once key per call. Worth adding when the office gets MCP write tools that are not idempotent.
- **The write path re-validates.** `execute-sql-write` allows INSERT, UPDATE, DELETE and also CREATE, DROP, ALTER and TRUNCATE after approval; the office refuses DDL always, because a task's agent has no business changing a schema. SSH `execute-command` audit-logs before and after (command cut at 500 characters, exit code, duration, whether the output was cut) and caps output at 50,000 characters; the office records the same on the task's timeline, masked.
- **What to lift into the office's MCP connectors next.** (1) A permission tier per team (use / read only), and a per-person override the way `tools` on a person already works. (2) `<alias>__<tool>` naming when two connectors expose the same tool name (or on request). (3) An `auto_include` connector every team gets. (4) A connector status with the last check and its message on the Tools & connectors screen, refreshed by a test button. (5) A run-once key per approved tool call, kept with the task, so a replay after a restart cannot run a non-idempotent MCP action twice. (6) Pinning an SSH host key on first use and showing it on the entry, instead of the optional fingerprint field.

## Out of scope
- Oracle, SQL Server and SAP HANA connectors (the intranet has them; the office needs Postgres and MySQL first).
- A schema cache: `db_schema` reads `information_schema` every time; a cache with a "stale after 30 days" flag as in the intranet can follow when a schema turns out to be slow to read.
- File read, write and delete over SSH (`sshReadFile`, `sshWriteFile`, `sshDeleteFile`): one command at a time covers the cases the office has today.
